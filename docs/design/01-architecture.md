# 01. アーキテクチャ

## 1. 処理の流れ

```
[アドレスバー] → Navigation
   → Loader（ブロッカー判定 → キャッシュ → HTTP/TLS）         … I/O スレッド
   → バイト列 → 文字コード判定 → HTML トークナイザ → ツリー構築 → DOM（不変）
   → サブリソース取得（CSS / 画像。各リクエストでブロッカー判定）
   → カスケード（UA + ブロッカー(user origin) + 作者 CSS）→ 計算済みスタイル
   → ボックスツリー → レイアウト → 描画リスト → ラスタライズ → 画面へ転送
```

## 2. プロセスとスレッド

- **シングルプロセス**。タブはすべて同一プロセス内の `hk_tab` として管理する。
- **メインスレッド**：Win32 メッセージループ、UI、HTML/CSS の解析、スタイル計算、レイアウト、描画。
- **I/O スレッド**：DNS（`GetAddrInfoExW`）、ソケット（IOCP）、TLS（SChannel）、圧縮の展開、画像の展開（WIC）、ディスクキャッシュの読み書き、フィルタリストのコンパイル。
- **スレッド間の通信**：
  - 片方向のメッセージキュー 2 本（main→io、io→main）。mutex と条件変数を使う単純な実装で十分。
  - I/O 側からメインスレッドへ渡すときは、キューに積んでから `PostMessage(WM_HK_IO)` で起こす。
  - データの所有権はメッセージと一緒に移す。両スレッドから同時に触る共有データは作らない。
- HTML のパースは、データが届くたびに少しずつ進める（メインスレッド上で、1 回あたり 8 ms ごとに処理を区切る）。

## 3. モジュール構成とディレクトリ

```
src/
  base/      アリーナ、可変長配列、ハッシュ表、文字列スライス、アトム、UTF-8、ログ、時刻
  plat/      プラットフォーム抽象（ヘッダのみ）
  plat/win32/ ウィンドウ・入力・IME、ソケット、SChannel、DirectWrite、WIC、ファイル、スレッド
  net/       URL、PSL、HTTP/1.1、Cookie、キャッシュ、ローダ、文字コード
  html/      トークナイザ、ツリー構築、文字参照表
  dom/       ノード、属性、文書
  css/       トークナイザ、パーサ、セレクタ、カスケード、値、メディアクエリ
  layout/    ボックスツリー、block、inline、float、position、flex、table
  paint/     描画リスト、ラスタライザ、グリフキャッシュ、画像キャッシュ
  blocker/   フィルタパーサ、コンパイラ、照合、要素の非表示、リスト更新
  shell/     ブラウザウィンドウ、タブ、アドレスバー、履歴、ブックマーク、設定、内部ページ
  main.c

tests/  fuzz/  bench/
```

### 依存の向き（逆向きの参照は禁止）

```
shell → (blocker, paint, layout, css, html, dom, net) → base
各モジュール → plat（抽象ヘッダ）← plat/win32（実装）
```

- `plat/` の抽象化は狭く保つ。対象は **ウィンドウ・入力・IME、ソケット・TLS、テキスト整形・グリフ、画像展開、ファイル、スレッド** の 6 つだけ。
- 将来 Linux に移植するときは、`plat/linux`（X11/Wayland、OpenSSL または mbedTLS、HarfBuzz と FreeType、stb_image など）を追加すれば済む形にする。

## 4. メモリ管理

### 4.1 基本方針

**DOM はパース後に変化しない**。これを最大限に活かす。

| 種類 | 寿命 | 確保方法 |
|---|---|---|
| 文書アリーナ | 1 回のナビゲーション | 64 KB 単位のチャンクを積み上げるバンプアロケータ。DOM、属性、テキスト、CSS のルール、計算済みスタイル、文書内アトム |
| レイアウトアリーナ | 1 回のフルレイアウト | ボックスツリーと行ボックス。全体を再レイアウトするときは丸ごとリセット |
| フレームアリーナ | 1 フレーム | 描画時の一時データ |
| 汎用ヒープ | 任意 | キャッシュ、タブ、ネットワークバッファなど、寿命がばらばらなもの |

- 個々のノードは解放しない。ページを離れたら、アリーナごと一括で解放する。
- アロケータは引数として明示的に渡す（`hk_arena *a`）。グローバルな malloc は base と plat の中でしか呼ばない。

### 4.2 ノードの表現

ポインタの代わりに、文書内の 32 ビット番号でノード同士をつなぐ。ポインタ（8 バイト）の半分の大きさで済む。

```c
typedef uint32_t hk_node_id;          /* 0 = なし */

typedef struct {
    uint8_t    type;                  /* element / text / comment / doctype */
    uint8_t    flags;                 /* 解析中の状態など */
    uint16_t   ns_and_misc;
    hk_node_id parent, first_child, last_child, prev_sibling, next_sibling;
    uint32_t   payload;               /* 要素データまたはテキスト範囲の番号 */
} hk_node;                            /* 24 バイト */

typedef struct {
    hk_atom    tag;
    hk_atom    id;
    uint32_t   attr_first; uint16_t attr_count;
    uint16_t   class_count; uint32_t class_first;   /* アトムの配列 */
    uint32_t   style;                 /* 計算済みスタイルの番号 */
} hk_element;
```

### 4.3 アトム（文字列の共有）

- **静的アトム**：既知のタグ名・属性名・CSS プロパティ名・キーワードは、`src/dom/hk_names.def` に列挙し、X マクロで番号（`HK_ATOM_div` など）を割り当てる。起動時に一度だけ表を作る（数百件で数マイクロ秒）。完全ハッシュは、計測で必要になってから検討する。
- **動的アトム**：class 名、id、未知の属性名は、文書アリーナ上の表に登録する。
- 比較は整数同士で行う。ブロッカーとの照合など文書をまたぐ場面では、64 ビットのハッシュ値を併用する。

### 4.4 タブごとのメモリを抑える段階的な破棄

| 状態 | 保持するもの | 移る条件 |
|---|---|---|
| 表示中 | すべて | — |
| 背景 | DOM とスタイル。描画リストと展開済み画像は破棄 | 非表示になった直後 |
| 休止 | URL、スクロール位置、フォームの入力内容だけ（約 1 KB） | 非表示のまま 10 分経過、またはメモリが逼迫したとき |

休止状態のタブは、表示されたときに HTTP キャッシュから再パースする。JS がないため、再パースは速く、状態も失われない。

## 5. セキュリティ

JavaScript がないので、攻撃者が任意のコードを動かす手段は「解析器のバグ」に限られる。

- **攻撃面**：HTML / CSS / URL / HTTP / 圧縮 / フィルタ構文の各パーサ（自作部分）、画像（WIC）、フォント（DirectWrite）、TLS（SChannel）。
- **自作パーサの対策**：入力はすべて `(ptr, len)` のスライスで扱い、境界を検査する関数を経由させる。全パーサにファジングを用意し（06 章）、デバッグビルドでは ASan を有効にする。
- **プロセスの緩和策**（起動時に自分のプロセスへ設定する。実装は `src/plat/win32/hk_plat_win32.c`）：
  - ビルドオプション：`/guard:cf`（CFG）、`/CETCOMPAT`（シャドウスタック）、ASLR（`/HIGHENTROPYVA`）、DEP
  - `SetProcessMitigationPolicy` で設定するもの：
    - 拡張ポイントの無効化（AppInit DLL、グローバルフック、IMM32 だけに対応した旧式の IME）
    - DLL の読み込み制限（ネットワーク上・低整合性レベルの DLL を禁止し、System32 を優先）
    - 不正なハンドルの検出
    - 動的コード生成の禁止（ASan のビルドでは、ASan が実行時にコードを書き換えるため設定しない）
  - 設定しないもの：
    - 子プロセス作成の禁止（「フォルダを開く」や外部プレイヤーの起動に必要なため）
    - システム外フォントの禁止（ユーザーが個別にインストールしたフォントが使えなくなるため）
    - Microsoft 署名の DLL のみの許可（サードパーティ製の IME が読み込めなくなるため）
- **メモリ**：マニフェストで Segment Heap を有効にする（従来のヒープより管理領域が小さい）。
- **将来課題**：画像の展開を、AppContainer で隔離した子プロセスへ分離する（必要になった場合）。

## 6. ビルドとコーディング規約

- **言語**：C17。VLA と、MSVC 固有の拡張は使わない。
- **警告**：`/W4 /WX`（clang-cl では `-Wall -Wextra -Werror`）。整形は clang-format。
- **命名**：公開シンボルは `hk_<モジュール>_<名前>`。型名は `hk_xxx`。マクロは `HK_`。
- **エラー処理**：戻り値の `hk_status`（列挙型）で返す。致命的な不整合は `HK_ASSERT`（リリースビルドでも有効）で検出する。
- **文字列**：`typedef struct { const char *p; size_t n; } hk_str;`。NUL 終端を前提にしない。
- **ビルドの種類**（`CMakePresets.json` のプリセット名）：
  - `debug`：ASan あり
  - `release`：`/O2`、LTO あり、CRT は静的リンク
  - `fuzz`：MSVC の `/fsanitize=fuzzer,address`（clang-cl でも可）
- **ジェネレータ**：Ninja を使う。Visual Studio Build Tools に同梱されている Ninja で足りる。CMake 4.0 は Visual Studio 18 用のジェネレータをまだ持たないため。
- **バイナリサイズの目標**：3 MB 未満（フィルタリストは含めない）。
